Barnark

A place for every folder, and a reason for it.

Without a shared architectural vocabulary, classes of every sort end up in any folder. Barnark starts a new project in the architecture you choose, gives every folder a meaning that says what belongs in it, and creates each new part in its right place. Would you know if a new developer had just saved an Application file into the Domain? With every folder’s meaning written down, anyone reading it can spot a file in the wrong place. In a barn it is the Architecture tab, and it works on its own in any project too.

No favourites

Any architecture. Several in one project.

Barnark has no style of its own. Pick from a catalogue of well-known shapes, and give each part of your project the one that suits it. An application’s core can be Domain Driven Design, its website Model View Controller and a shared library a Library, all in one project. Every template says what it suits, and Barnark shows its shape before you pick it.

One click

Pick an architecture. Get the folder.

Click Clone into the project, choose the architecture your project should follow, name your copy of it, and the folder is created with its whole structure. Each choice has a description recommending what that architecture is best suited for. Its folder structure is shown, so you can see how the architecture looks before anything is made.

No copying and pasting necessary. Just click and go.

Meaning

Every folder says what it is for.

Each folder in a template has a meaning in plain words: what belongs in it, and which way its dependencies point. A team that has never talked about dependency direction learns that there is such a thing, just by reading its own architecture.

Dependency direction is taught, not enforced. Following it stays a human matter, and a team that wants enforcement can add a tool such as deptrac.

Domain Driven Design · a bounded context
Domain/
The core business logic and rules, expressed as Aggregates, kept independent of delivery mechanism and infrastructure. It depends only on its own Context’s Domain and PublicApi and on the Domain Kernel, never on another Context.
PublicApi/
The only part of a Context another Context may depend on: what it publishes about itself, with its internals kept behind it.

Word for word from the bundled template.

Conformance

Has anything strayed? Ask.

Nobody has to declare a project “well architected”. Press a button, or run one command, and Barnark checks your project’s folder against its architecture. Either it comes back clean, or it names each folder that doesn’t belong, and where.

It’s the same idea as a proven story in Barnspec, applied to structure: the evidence decides, not opinion.

Honest about its scope

Made for new projects.

Barnark keeps a new project well shaped from its first commit. It isn’t for judging a codebase that never followed an architecture: a check over one would list a great many problems, and that isn’t what it’s for. It looks after folders, not files, and it teaches dependency direction rather than enforcing it.

Yours to keep

Your own copy, tied to nothing.

When you make a folder, Barnark copies the template into a template of your own, under the name you give it. Nothing ties the copy back: a later change to the catalogue never reaches it, and nothing in your project names the template it came from.

Your project’s template is kept as revisions, and none is ever changed in place. Adding a context or a feature adds it to the template as a new revision, and so does deleting one. Barnark writes each revision's reason. The History tab lists them, and shows each as a read-only tree.

Templates are Barncept concepts, each with a description of what it is and what it suits, and a meaning for every folder. Barnark reads one only to copy it, into your project’s template or another of your own; from then on the copy is yours.

Checking a projectSlots and exclusions

A template describes a shape, not your code: its parts are the folders it names itself, and “Context” is a slot your own folders fill. Barnark works out which slot each folder fills from the project’s template and records it, so your contexts are checked where they actually are. Anything it can’t settle is listed. Files are never checked: a template says only what folders there are.

Paths with no architectural meaning, like test fixtures, can be excluded.

What gets createdFolders, with their whole structure

A folder you name arrives with its whole fixed structure, and a folder created empty keeps a .gitkeep so that git keeps it. Apart from that, Barnark never creates a file in your folders. Nothing already on disk is overwritten. Adding or removing a folder you named is a new revision of the template. Each template of your own is kept in .barnark/templates/ (in a barn, .barn/barnark/templates/).

The command lineFor scripts, agents and terminal lovers 
$ barnark template:clone "Domain Driven Design" Shop src    # your project's template, Shop, and src/
$ barnark template:offers src/Context                       # what may be created here?
$ barnark template:new Context Billing src/Context
$ barnark template:check                                    # check src/ against Shop
$ barnark template:copy Shop Market                         # a template of your own

The folder your project’s template is bound to is recorded in .barnark/tracked-folders.json (in a barn, .barn/barnark/tracked-folders.json), committed with your code and the templates, so a check needs no arguments.

Get started

Start your project in shape.

Barnark needs PHP 8.5 and Composer. Install it into a new project, run one command from anywhere in it, and add your first folder.

$ barnark gui
InstallationInstall from Packagist

Require Barnark, its command line and its browser app. Composer pulls in Barncept and Barnscaff.

$ composer require --dev rmb32/barnark rmb32/barnark-cli rmb32/barnark-gui
